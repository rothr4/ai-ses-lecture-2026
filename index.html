AIで変わるSESの仕事と、今から身につけること

株式会社EDIX　倉谷参加者：約20名／講話50分＋質疑
今日はAIの機能紹介ではありません。私自身の開発方法がどう変わったかを材料に、SESの仕事と単価がこれからどう変わるかを考えます。
私に起きた変化02 / 18
私はいま、開発の9割を
スマホからやっている。

コードをスマホで打つのではない。開発サーバ上のClaudeへ指示し、結果を確認し、次の判断を返す。

移動中指示と確認が進む
2〜3件高密度案件を並行
役割転換入力から判断へ
空き時間まで働こうという話ではありません。必要なときに場所を選べるようになった、という話です。私の開発現場からPCがほぼ消えたように、将来はスマホを操作する時間自体も減るかもしれません。[Sources] OpenAI image generation. Prompt: Japanese software PM remotely developing from a smartphone on a commuter train; warm documentary realism; no logos or readable text.
私に起きた変化03 / 18

「コードが速く書けた」だけではない。
PMである私の時間まで減った。

比較項目従来型の外注開発現在のAI駆動開発
実装主体外注チームへ要件を説明して依頼Claudeと複数のAIエージェント
私の時間会議、説明、進捗確認、レビューに拘束される要件、例外判断、最終承認へ集中する
開発場所PCを開き、開発環境へ接続するスマホから開発サーバへ指示する
並行案件高密度な案件は基本的に1件同等密度の案件を2〜3件並行
総合生産性基準：1私の体感：約10倍
まだ測定値ではない。 今後は期間、私の実作業時間、不具合、手戻りを案件ごとに記録する。
10倍は現時点では私の体感です。誇張して一般化するのではなく、今後は実案件で測定します。それでもPMの拘束時間が減り、並行案件数が増えた事実は、生産構造の変化を示しています。

実際の進め方05 / 18

スマホから指示して、どこまでAIに任せているのか

01
目的を渡す要件・制約・完了条件をスマホから送る
02
役割を分けて回す調査、実装、別視点レビュー、CIを並行・反復
03
根拠を見て承認する差分、テスト結果、残るリスクを人間が判断
私が書く量は減った。しかし、決める量と責任は減っていない。
AIの一発回答を採用しているわけではありません。調査、実装、レビュー、テストを役割として分け、最後に私が承認します。この構造があるので、スマホが入口でも品質を維持できます。[Sources] OpenAI image generation. Prompt: Japanese project manager coordinating three parallel software workstreams from a smartphone; calm home office; abstract unreadable boards.
品質06 / 18

AIは速い。だから、間違いを止める仕組みを先に置く。

よく起きる失敗そのまま進むと止める仕組み
要件を都合よく解釈する動くが、欲しかったものと違う要件・禁止事項・完了条件を文書化
局所修正だけを見る別機能や既存仕様を壊す影響調査、回帰テスト、CI
自信ありげに誤るレビュー側も見逃しやすい別エージェントによる敵対レビュー
変更範囲を広げすぎる戻すのが難しくなる小さな差分、ブランチ、Git履歴
秘密情報を含める漏えい・契約違反につながる利用ルール、秘密情報スキャン、承認環境
Claudeを契約しただけでは10倍にならない。ルール、テスト、レビュー、Gitまで含めて一つの開発体制。
AIを魔法として使うのではなく、高速だがミスもする作業者として扱います。品質が上がったのは、モデルだけでなく、失敗を止める仕組みを作ったからです。
市場が変わる理由07 / 18

AIが任される仕事は、コード補完から
「数時間かかる一連の作業」へ伸びている。

以前の使い方現在増えている使い方
コードの続きを出すリポジトリを調査する
関数を一つ作る複数ファイルを修正する
質問に回答する実行結果を見てやり直す
人が手順を指示するAIが手順を組み立てる

ただし、METRの評価には条件がある

  • 主にソフトウェア、ML、サイバー領域
  • 目的と正解を明確にしやすいタスク
  • 既存社員より、文脈の少ない新人・外注者に近い
  • 50%成功は、本番品質を意味しない
だから最初に影響を受けるのは、仕事が消える職種ではなく、AIへ渡しやすい作業。
出典：METR「Task-Completion Time Horizons of Frontier AI Models」
AIが全職業を自動化したという話ではありません。評価対象は低文脈で自己完結した作業です。ただ、その条件が若手や外部委託へ渡される仕事と重なる点を重く見ています。[Sources] https://metr.org/time-horizons/

Java、インフラ、テストという職種単位で消えるのではありません。同じ職種の中でも、明確で文脈の少ない作業から価格圧力がかかります。
若手への影響09 / 18

一番怖いのは、若手が不要になることではない。
経験を積むための仕事が減ることだ。

01
AIの答えを疑う不足したテスト、壊れる条件、副作用を探す
02
小さく一周する要件、実装、テスト、説明まで自分で持つ
03
判断を言葉にする採用理由、残るリスク、品質根拠を説明する
基礎を飛ばさない。AIを使って、基礎から設計までの周回数を増やす。
AIで簡単な仕事を飛ばすと、若手は自然には育ちません。だから会社と本人が意図的に一周の経験を作る必要があります。[Sources] OpenAI image generation. Prompt: junior Japanese engineer and senior mentor reviewing AI-generated code and tests; warm daylight; documentary realism.
SESの商売10 / 18

人月市場に、「トークンで買える作業能力」が入ってきた。

比較SESエンジニアAIエージェント顧客が見るポイント
購入単位人月・時間プラン・トークン・API同じ成果に何人・何日必要か
並列化採用・契約・引き継ぎが必要比較的すぐ増やせる納期と費用がどこまで縮むか
文脈現場で蓄積できる人間が渡す必要がある業務理解まで任せられるか
責任組織と人が負える負えない事故時に誰が説明するか
SESが消えるのではない。AIへ渡しやすい作業だけを時間で売ることが、難しくなる。
顧客は明日から全員をAIへ置き換えるわけではありません。ただ、見積もりや期待納期にAI利用が織り込まれれば、同じ作業時間を同じ単価で売り続けるのは難しくなります。
市場の変化11 / 18

1案件の必要人数は減っても、
作られるシステムの総量は増える可能性がある。

圧縮されやすい

  • 手作業のコーディング
  • 定型的なテスト作成
  • 転記・定型文書
  • 低文脈の調査作業

増えやすい

  • レガシー刷新
  • 小規模な業務システム
  • AI導入・データ整備
  • セキュリティ・品質保証

人間中心で残る

  • 顧客との合意形成
  • 本番環境の判断
  • 業務ルールの決定
  • 事故時の説明責任

開発費が下がれば、今まで予算化できなかったシステムが作られます。案件数が増えても、作業者だけを大量に集めるモデルは弱くなる可能性があります。一方、日本企業はDX・AI人材をまだ大きく不足と捉えており、人材育成も追いついていません。[Sources] https://www.ipa.go.jp/digital/chousa/dx-trend/dx-trend-2026.html

何を始めるか13 / 18

同じ教材を受けても、現場で使う場所は職種ごとに違う。

現在の役割最初にAIへ任せる自分が確認する見せられる成果
テスト・QA観点、境界値、テストデータ、ケース案網羅性、優先順位、業務上のリスク追加した観点と検出した欠陥
開発実装案、リファクタ、テスト、影響調査設計理由、副作用、例外、保守性要件からテストまでの一連の変更
インフラ・運用IaC案、ログ分析、手順書、監視条件権限、破壊性、本番影響、復旧方法再現可能な構築と復旧手順
リーダー・PM要件分解、論点整理、進捗要約、レビュー優先順位、合意、費用、品質、責任範囲少人数で成立させた案件実績
目標は「AIを使った」ではなく、自分の仕事で何が速くなり、何の品質が上がったかを説明すること。
アプリ開発だけがAI学習ではありません。テスト、運用、インフラにも入口があります。今の役割に近いところから始め、確認したことまで成果として残します。
市場価値の見せ方14 / 18

経験年数だけでなく、「AI込みでどこまで担当したか」を書けるようにする。

従来の説明これから強くなる説明
Javaを3年経験AIを併用し、影響調査・実装・テスト・レビューまで担当
単体テストを担当AIでテスト案を作り、境界値と業務観点を追加して欠陥を検出
運用手順書を作成既存資料を構造化し、AIで標準手順と例外時の復旧手順を整備
障害調査を経験AIでログと変更差分を分析し、原因候補と確認結果を説明
リーダー経験あり複数AIへ調査・実装・レビューを分担し、品質と納期を管理

「何を知っているか」だけでなく、何を完成させ、どう確認したか。

AIツール名を並べるだけでは弱いです。AIを使って担当範囲がどう広がり、どんな成果と品質を出したかをスキルシートで説明できる状態を目指します。
AIを使う側の仕事15 / 18

任せる範囲が広がっても、最後に人間が持つ仕事は残る。

仕事AIへ任せやすい部分人間が持ち続ける部分
要件論点整理、質問案、仕様の下書き目的、優先順位、顧客との合意
設計・実装代替案、コード、変更、説明文採用判断、全体整合、技術的責任
テストケース生成、実行、自動修正十分性判断、業務リスクの受容
運用ログ分析、原因候補、復旧案本番操作の承認、停止・復旧判断
顧客対応資料、要約、説明案交渉、謝罪、信頼、最終説明
AI人材とは、プロンプトが上手い人ではなく、この境界を決めて品質に責任を持てる人。
プロンプト技術は変化が速く、すぐ標準化されます。長く価値が残るのは、目的、文脈、検証、責任の境界を設計する能力です。
顧客現場での利用16 / 18

使えるかどうかは、データ・契約・環境で判断する。

そのまま試しやすい

公開情報、個人の学習課題、架空データ、機密を含まないサンプルコード。

会社が認めた学習環境で、まず完成経験を作る。

承認条件を確認する

社内コード、業務資料、実データ。利用できるAI、契約、保存、学習利用、ログ管理を確認。

承認済みの法人環境や閉じた開発環境を使う。

無断で入力しない

顧客コード、個人情報、認証情報、未公開仕様を個人アカウントや未承認サービスへ送る。

AI禁止現場で、こっそり使うことはしない。

安全に使える条件を判断し、顧客へ説明できることも、AIを使うエンジニアの能力。
使えない現場で無断利用することを推奨しません。AI禁止の現場でも、会社の安全な環境で学び、公開情報や架空データで能力を伸ばすことはできます。
講話後の行動17 / 18

90日後、「教材を見た」ではなく
一つの完成物と検証記録を残す。

期間本人が行うこと残す成果会社が用意すること
1〜30日教材を進め、安全な課題で毎日触る成功・失敗した指示、確認項目、学習ログ利用ルール、推奨教材、安全な検証環境

完成物動く・使えるものを一つ
根拠なぜ品質が十分か説明
比較時間・範囲・品質の変化
次の課題自分で見つけて言語化
教材だけでは市場価値になりません。完成物、品質の根拠、従来との比較を残して初めて実績になります。本人に行動を求める以上、会社も環境と評価を用意します。
